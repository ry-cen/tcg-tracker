# Verification

Run `npm run verify` for the required application, recovery and release-runtime regression gate. Supply `TEST_ADMIN_DATABASE_URL` as a loopback PostgreSQL URI with permission to create/drop disposable databases. The runner copies the working tree, allocates its own databases, ports and private artifact directory, and removes its processes and databases after the run. Installed Node/Python dependencies are reused; build output and test fixtures belong to the copied workspace. Runs have separate build output and logs, but run one full or fast gate at a time on one host: a gate already uses most of the host's cores, and a second gate's load would reach the tests that must run alone. Narrow runs (`--suite api` or `--suite browser` with selectors) need not wait for another gate to finish. Keep the host awake for the whole run (on power, lid open): the runner holds off idle sleep with `caffeinate` where it exists, but a sleeping host stops the tests' processes while wall-clock time runs on, and Docker's database clock lags the host's after a wake. When that happens `verification.log` ends with a `== WARNING:` line and `result.json` records `host_suspended_seconds` and `database_clock_skew_seconds`; timing and approval-code expiry failures from such a run are not evidence, so rerun it. A host network change (an interface or address coming or going, such as a dock, VPN or Wi-Fi) makes Chromium drop the page's in-flight requests with `net::ERR_NETWORK_CHANGED`, and a page whose modules were dropped never starts. The runner searches each failed Playwright test's trace for that error; for each hit `verification.log` gets a `== WARNING:` line naming the test and `result.json` lists it under `network_warnings`. The dropped request may be unrelated to the failure, so check the trace: when the dropped requests caused it (for example a blank page after module loads failed), the failure is not evidence either, so rerun the test.

The runner checks the current working-tree source, including staged changes. Git history is read only to build the historical runtime regression fixture; a fresh clone needs full history. The repository workflow (`.github/workflows/verify.yml`) runs the fast tier (`--fast`) on pull requests and before each dev deploy (pushes to other branches are checked once their pull request opens): the slow capacity and timing tests fail at random on hosted runners. It splits the fast tier into 14 legs that run at once, each on its own runner with its own database server: `--suite api --fast --shard K/3` for K from 1 to 3, `--suite auth --fast` (guardrails, the build and vitest, run once for every leg) and `--suite browser --fast --shard K/10` for K from 1 to 10. On one runner the fast tier took about 32 minutes; a leg takes about 5. A job named `verify` passes only when every leg passed (or, on a full dispatch, the full job), so pull requests and the dev deploy wait on that one check, and each leg uploads its own artifact, `verification-<leg>` (such as `verification-api-2` or `verification-browser-7`). The burn-in (below) runs locally only, before a pull request that adds or changes tests. The full gate runs locally, or on CI from Actions → Verify → Run workflow with **full** ticked, as one unsharded job whose artifact is `verification`. Making the `verify` job a protected-branch requirement remains repository-host configuration.

## Loops

| Command                                                       | Runs                                                                                                                            | Enough for                                      |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `npm run verify -- --suite api -- <pytest selectors>`         | the selected `api/tests` tests; without selectors all of `api/tests`, nothing else                                              | iterating on API code and its tests             |
| `npm run verify -- --suite browser -- <Playwright selectors>` | the selected Playwright specs against fresh stacks                                                                              | reproducing a browser failure                   |
| `npm run verify -- --fast`                                    | the whole gate without `slow` pytest and vitest tests, `@slow` Playwright tests and the operations (release and recovery) suite | a worker's check; CI runs this split into legs  |
| `npm run verify -- --suite api --fast --shard K/3`            | the K-th of 3 parts of the fast `api/tests` tests, whole files                                                                  | reproducing one CI api leg                      |
| `npm run verify -- --suite browser --fast --shard K/10`       | the K-th of 10 parts of the fast Playwright tests, whole spec files, without guardrails or the build                            | reproducing one CI browser leg                  |
| `npm run verify -- --burn-in --fast`                          | the vitest files and Playwright specs changed against `origin/dev`, each repeated under parallel load                           | new or changed tests; run locally before the PR |
| `npm run verify -- --suite browser --repeat N -- <selectors>` | the selected Playwright tests N times each, spread over the stacks                                                              | showing that a browser flake fix holds          |
| `npm run verify`                                              | everything                                                                                                                      | acceptance; run locally (CI on demand)          |

```sh
npm run verify -- --suite api -- api/tests/test_prices.py -k stale
npm run verify -- --suite browser -- web/tests/workspace-actions.spec.ts
```

API selectors are pytest node ids, paths and options such as `-k`, `-x` or `--lf`; the runner sets `-m`, `-n`, `-p` and `--dist` itself. Browser selectors are spec files or `file:line` locations. `--fast` combines with `--suite api`, `--suite auth` and `--suite browser`. A bare `pytest <nodeid>` does not work for most API tests: they need the gate's migrated database and environment. `npm run test:fast` is unchanged: it is the guardrails-only check the pre-commit hook runs, not the fast tier.

`--shard K/N` runs the K-th of N parts of `--suite api` or `--suite browser`, whole test files at a time, in both passes: every test lands in exactly one shard, and the N shards together run what the unsharded suite runs. `api/tests/conftest.py` makes pytest's split from everything collected, before `-m` and `-k` deselect anything, so both passes and every pytest-xdist worker agree; files go heaviest first to the lightest shard, weighed by their tests not marked `slow`, and the other shards' tests count as deselected, not skipped. Playwright splits with its own `--shard`, and `fullyParallel: false` in `playwright.config.ts` keeps each spec file in one shard. A shard whose serial pass matches nothing is normal, but a shard in which neither pass runs a test fails, like an unsharded run with no matching test; selectors combine with `--shard`, so narrow selectors can leave a shard empty, and path or node-id selectors change what is collected and so the split: to rerun a test that failed in a CI leg, select it without `--shard`. A shard without selectors takes a gate's share of the host, so it counts as a gate, not a narrow run. A browser shard skips `npm run guardrails` and `npm run build`: its stacks serve the web app through the vite dev server, and on CI the auth leg runs both once. An unsharded `--suite browser` still runs them.

`--repeat N` runs each selected Playwright test N times (`--repeat-each`), or with `--suite auth` the whole vitest run N times, one after another; vitest has no per-file repeat that also re-runs a file's `beforeAll`, where its server startups live.

## Burn-in

`npm run verify -- --burn-in` repeats the tests a branch changes, in the same copied workspace with its own databases, ports and stacks as every other run. It compares the working tree (commits, staged and unstaged changes, untracked files) with its merge base with `--base` (default `origin/dev`) and chooses every vitest file (`auth/tests/**/*.test.ts`) and Playwright spec (`web/tests/**/*.spec.ts`) that changed or imports a changed file under `auth/tests` or `web/tests`, directly or through other support files: a change to `web/tests/support/motion.ts` chooses the specs that import `touch-target.ts`, which imports it. A changed file that no test imports (`browser-stack.ts`, the configs) chooses nothing; the ordinary gate covers it. With nothing chosen the run ends at once with exit code 0, and `result.json` records the empty plan under `burn_in`.

Playwright runs the chosen specs in its two passes with `--repeat-each R`, so the copies of one spec run at once on different stacks and `@serial` tests still run alone. R is 10 when the chosen tests fit a budget of 240 test runs, otherwise 240 divided by their number, and never below 3. The budget was sized on CI, where the burn-in used to run: the fast tier's 144 Playwright tests took 395 s on a 4-core hosted runner with 2 stacks, so 240 runs take about 11 minutes there (about 4 locally). Ten repeats catch a new flake that fails one run in five with a probability of 89%, three repeats with 49%, so the burn-in is a screen for frequent flakes, not proof against rare ones. vitest runs the chosen files 5 times, one invocation after another, because copies of one file at once would share its ports and the gate's database; each invocation restarts the servers the files start. `--fast` leaves out `@slow` and `slow` tests as everywhere else, and a vitest file tagged `// @module-tag slow` drops out. `--repeat N` overrides both counts. The first lines of `verification.log` (`== burn-in:`) name the merge base, the chosen files and the counts; vitest's reports are `vitest-1.xml` to `vitest-N.xml`, and the summary adds them up.

A ticket is accepted on the tests relevant to it: the narrow loops over the API tests and browser specs it adds or touches, plus `npm run check` and `npm run guardrails`. Its evidence names those runs and quotes their counts. The full default gate runs once per feature, after its last ticket and before the pull request to `dev`, and the pull request quotes the counts from that run's `verification.log` summary. When the branch adds or changes tests, run `npm run verify -- --burn-in --fast` before the pull request too and quote its counts; CI does not run it.

## Parallelism and tiers

pytest runs in two passes. The first runs every test not marked `serial` with pytest-xdist, one worker per prepared database; `--dist loadfile` keeps each file's tests together and in order. Each worker has its own database, projection directory, runner lock directory, catalog fixture directory and mail file (`scripts/verify_resources.py`, applied by `api/tests/conftest.py`). The second pass runs the `serial` tests in one process with nothing else running.

- Mark a test `serial` when it asserts an upper bound on elapsed time or a latency percentile, or launches real runner processes. Tickets that add price or budget tests with elapsed-time bounds mark them `serial`.
- Mark a test `slow` when it launches real processes, waits out real wall-clock intervals, sleeps a second or more, or builds a capacity-sized data set.
- Both marks take a `reason`; a `slow` reason starts with `process:`, `wall-clock:`, `capacity:` or `sleep:`. `scripts/check_guardrails.py` checks the reasons and requires both marks on tests that use the `proc` runner fixture.

Playwright runs one application stack per worker: its own database, API, auth and web servers, mail file, projection, runner lock and catalog fixture directories. `web/tests/support/browser-stack.ts` points each worker at its stack, so specs in different workers never share data; the tests of one file still run in order in one worker. Every test on a stack signs in with the same owner email, so the workspace specs start each test as a new owner (`startAsNewOwner` in `web/tests/support/owner.ts`, called by their `signIn`): the test sees only the Locations it makes, whatever earlier tests or burn-in repeats on that stack left behind. A new `workspace-*.spec.ts` whose `signIn` skips it fails the guardrails; it refuses to run outside a verification stack, since it deletes the owner's account. Tests tagged `@serial` run afterwards with one worker and say why in a comment; `price-refresh.spec.ts` is serial because its label depends on a real runner's deadline inside the server's wait window. Tests tagged `@slow` say their category in a comment.

A spec that needs more than one collector (the social network, #247 onward) imports `test` from `web/tests/support/collectors.ts`. Its `collectors` fixture's `signIn()` signs a new collector in, in its own browser context, then takes that account out of the owner seat (another email, no provider links, no owner binding): it stays signed in as a separate account, and the next owner sign-in makes a new one. Sign the test's own page in after the other collectors when it must be the owner; a page signed in before a `signIn()` call stays signed in but no longer holds the seat. The fixture closes the contexts it opened. Like `startAsNewOwner` it refuses to run outside a verification stack. `web/tests/collectors.spec.ts` is its self-test.

Worker counts follow the host: pytest `min(6, max(2, cores / 2))`, browser stacks `min(4, max(2, cores / 3))`. `--pytest-workers N` and `--browser-workers N` override them; `1` runs that suite in one process as before.

Vitest (`auth/tests`) runs its files in parallel, as before; each file's tests run in order. A whole file is slow with a `// @module-tag slow` line, a single test with `{ tags: ["slow"] }`; either carries a `// slow (<category>): why` comment, and the `slow` tag is defined in `vitest.config.ts`. `--fast` passes `--tags-filter=!slow`, so those tests count as skipped and a fully slow file starts none of its servers. The price-runner, deck-cost, price-refresh and published-cost files are slow (they start the multi-process price stacks), as are the public-records rebuild test (real API and auth processes) and the tests that wait out the gateway's 3 s budget or the mail relay's 5 s timeout. Those two limits are production constants with no test seam, so their tests keep real time.

Timing tests use real time only where they say why. The hard-stop and SIGSTOP runner scenarios scale the runner's contract constants through the test sitecustomize (see `docs/price-refresh.md`); the cold-start measurement and the idle-exit checks keep real time.

## Artifacts

Each run prints its `.scratch/verification/<run>/` directory. It holds:

- `verification.log`, ending with a summary: phase seconds, pytest, vitest and Playwright totals, and the slowest tests;
- service logs: `api.log`, `auth.log` and `web.log` for the first stack, `stack-<n>/` for the others;
- `browser/parallel/` and `browser/serial/` (Playwright output), `playwright-parallel.json`, `playwright-serial.json`;
- `pytest-parallel.xml`, `pytest-serial.xml`, `vitest.xml` (per-test times), `phases.tsv`, `timings.md`, `timings.json`;
- `result.json`: exit code, suite, selectors, `fast`, `shard`, worker counts, databases, timings.

The runner prints `Verification run: <id>` before anything else, so a run that is stopped early still names its directory. Remove a run with `.venv/bin/python scripts/verify_discard.py <id>`, which refuses anything but one existing run directory; never `rm -rf` a path built from a captured id, because an empty id removes every run's evidence.

Before it creates anything, each run drops the databases of verification runs that were killed before their own cleanup (`scripts/verify_reaper.py`). The runner tags every database it creates with an owner record in the database comment: the run id, a hashed id of the host, the `verify.py` pid and that process's start time. A run's databases are dropped together, and only when its owner ran on this host and has exited, the record is at least a minute old, and no session is connected to any of them; the drop never uses `WITH (FORCE)`, so a session that connects late keeps its database. The console and the first lines of `verification.log` report each decision as `== reaper:` lines, and `result.json` records them as `reaper` and `reaped_databases`. Untagged `tcg_verify_*` databases, made by an older harness on another branch or by a run killed while creating them, are kept and reported: drop one by hand only when no gate is running on any checkout. Databases that tests create themselves (`tcg_prices_*`, `tcg_recovery_*`, `tcg_release_*` and others) are not reaped.

Read counts from `verification.log`, not from the exit code. Failed runs keep the same diagnostics. These logs contain synthetic fixture data. `--suite auth` and `--suite operations` isolate those checks for diagnosis.

The pre-commit hook runs staged Prettier, TypeScript/generated-contract checks and database-free privacy guardrails. Generated clients remain generator-owned and are excluded from formatting. The hook does not require a running database; the full gate runs locally or on demand in CI.

Recovery, runtime readiness, activation/rollback/tamper, proxy-isolation, key-redaction and release-failure regressions run in the ordinary gate. Runtime fixtures are built in a temporary directory from repository history and current source. Their synthetic integrity receipts are test-only fixtures, not CI attestations or deployable releases. They never depend on artifacts left by an earlier agent session. The expensive exact-commit predecessor/successor release drill remains an explicit opt-in command documented in `docs/operations/release.md`; its skip is not a passing drill. `--fast` leaves the operations suite out; the full gate and `--suite operations` run it. A change to release, recovery or `tests/operations` code should also run `npm run verify -- --suite operations` before it is handed back.

For changes to verification, also run `npm run guardrails`. Mechanical release-transport, exception-output, process-scope, test-tier, flake-pattern and colour-token rules (no arbitrary colour values such as `bg-[#123]` in `web/src` or `web/index.html`) live in `scripts/check_guardrails.py`. The flake rules reject `page.waitForTimeout`, `expect(await <locator>.<read>())` one-shot reads of browser state, and touch-target sizes checked outside `expectTouchTarget` in `web/tests`, and counted loops that sleep in `auth/tests` (wait to a deadline with `auth/tests/support/servers.ts`). A quiet period before a negative check, a sample of an invariant, or a counted retry that is not a wait carries a `// flake-exempt <rule> (<category>): why` line in the comment block directly above the flagged line; extending those rules requires positive and negative examples in `tests/tooling` rather than duplicating them in AGENTS.md. Harness logic has unit tests in `tests/tooling/test_verify_harness.py`; the reaper also has a PostgreSQL test in `api/tests/test_verify_reaper.py`, which runs in the gate's pytest pass.
